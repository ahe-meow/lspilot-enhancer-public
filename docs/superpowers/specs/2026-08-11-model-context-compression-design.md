# LSPilot Enhancer 模型驱动上下文压缩设计

- 日期：2026-08-11
- 基线：`v1.7.4-preview.23`，commit `57a965a`
- 状态：设计已由用户逐段确认，等待书面规格审阅
- 范围：自动压缩、手动压缩、摘要请求、请求上下文替换、压缩状态持久化和压缩相关 UI 状态

## 1. 目标

将当前“发送前本地压缩并替换请求体”的行为改为模型驱动的会话压缩流程：

1. 每个完整 assistant、thinking、tool call 或 tool result 事件结束后检查上下文长度，不按流式 token/chunk 检查。
2. 上下文超过阈值时，在安全边界启动压缩，阻塞后续模型请求。
3. 使用当前对话选中的 Provider 和模型，复制当前请求的完整配置，让模型一次性生成固定 Markdown 结构的完整摘要。
4. 摘要成功后，模型请求只使用摘要基线和压缩边界之后的消息；宿主屏幕历史不删除、不重载，摘要正文不上屏。
5. 如果压缩时已经有待发送的用户消息，该消息先在屏幕显示，但不进入摘要请求；摘要完成后自动以“摘要 + 该用户消息”恢复请求。
6. 压缩期间发送和停止按钮灰化禁用。输入框仍可编辑，但尚未发送的文本不计入阈值、不进入摘要。
7. 摘要和压缩边界按会话持久化，进程或应用重启后继续使用；历史被编辑、删除或切换分支时使摘要失效。

## 2. 非目标

- 不修改宿主会话中的原始聊天记录。
- 不把摘要正文、压缩成功提示或压缩状态字段发送给 Provider。
- 不向宿主数据库写入隐藏的模型消息作为摘要载体。
- 不新增独立的摘要 Provider 或摘要模型配置。
- 不实现 UI 自动化测试；设备上的按钮状态、消息显示时序和视觉效果由人工验收。
- 不在本次设计中重做现有 Provider 协议、鉴权或缓存策略；摘要请求必须复用宿主现有请求链。

## 3. 已确认的业务决策

### 3.1 消息与请求

- 摘要请求使用当前对话的 Provider、模型、system prompt、工具定义、请求参数和 Provider 参数。
- 摘要请求排除触发阻塞的用户消息；摘要成功后该消息只在恢复请求中出现一次。
- 上下文阈值只统计已进入会话的消息，不包含输入框中的 `pendingInput`。
- 每个完整消息事件后检查。若工具调用尚未与结果配对，先标记待压缩，允许当前 tool call/result 链完成，再在安全边界压缩。
- 只在存在被阻塞的待继续内容时，压缩完成后自动发起恢复模型请求。若当前回复已完成，则只保存摘要并等待下一条用户消息。
- assistant、thinking、tool call 和 tool result 事件在提交到宿主显示层之前参与阈值与安全边界判断。触发压缩的非用户事件会保存在待恢复区，并计入摘要源；在摘要成功提交后、任何普通恢复请求发起之前，按原顺序补充上屏。它们不因恢复请求失败而永久隐藏，也不会被重复发送。被压缩边界覆盖的旧请求内容不再发送，但屏幕仍保留。

### 3.2 摘要内容

摘要必须是 Markdown，并严格按以下顺序包含七个部分：

1. `核心任务状态`
2. `行为设定`
3. `分阶段的对话历史概要`
4. `关键信息与关键上下文`
5. `最近 N 轮格式化完整上下文`，其中 `N` 默认为 3，用户降级时为 2 或 1
6. `当前激活的 skill/函数/工具/MCP 等包信息`
7. `后续执行要求`，正文要求继续完成任务；无任务时输出总结

“一轮”从一条 user 消息开始，包含其后的 assistant 正文、thinking、tool call、tool result 及后续 assistant 内容，直到模型停止回复并等待下一条 user 消息。工具调用和结果必须按原始顺序成对保留。

### 3.3 失败与超限

- 摘要请求失败、超时或 Markdown 格式不合规时自动重试一次。
- 重试后仍失败时不更新摘要、不发送被阻塞消息，保留原上下文和输入内容，并通过本地系统消息提示用户重试或取消。
- 如果失败的唯一原因是保留最近 3 轮后，重建的摘要请求仍超过阈值，则让用户选择：保留 2 轮、保留 1 轮或取消压缩。选择 2 轮或 1 轮后各发起一次新的摘要请求并完整校验，不再对同一轮数自动重试；选择 2 轮但仍超限时再次显示“保留 1 轮/取消压缩”，选择 1 轮仍超限时只显示“取消压缩”。取消则保留原上下文并解除阻塞，下次发送再次检查。
- 压缩后可见模型上下文必须低于配置阈值，而不仅仅是比原上下文更短。
- 摘要请求 token 不计入会话上下文和阈值，但 Provider 按自身实际规则计费和记录用量。

### 3.4 状态提示

- 正式进入摘要请求时立即显示并持久化模块本地系统消息，例如“正在压缩上下文，请稍候……”。
- 如果仍在等待未闭合的工具链，只显示“等待当前工具调用完成后开始压缩”，不提前宣称摘要已经开始。
- 成功时追加本地系统消息，包含压缩前 token、压缩后 token、减少量和压缩率。
- 失败、超时或取消时追加本地系统消息，明确原上下文未改变。
- 这些系统消息只供屏幕和模块状态使用，不进入摘要源或 Provider 请求。

## 4. 架构

### 4.1 请求层状态机

以现有 `ManualCompressionManager` 为协调入口，在请求层维护按会话隔离的状态：

```text
IDLE -> WAITING_SAFE_BOUNDARY   （超阈值且仍有未配对 tool call）
IDLE -> SUMMARIZING             （超阈值且已在安全边界）
WAITING_SAFE_BOUNDARY -> SUMMARIZING
SUMMARIZING/RETRYING -> VALIDATING
VALIDATING -> IDLE              （提交成功）
VALIDATING -> RETRYING          （首次失败）
VALIDATING/RETRYING -> AWAITING_USER_ACTION
AWAITING_USER_ACTION -> RETRYING（用户重试或选择 2/1 轮）
AWAITING_USER_ACTION -> IDLE    （用户取消，原上下文不变）
```

每个任务携带 `chatId`、任务 ID、压缩边界指纹、Provider 签名和保留轮次数。只有任务仍是当前会话的活动任务时，响应才可以提交；切换会话、切换分支、编辑/删除历史或开始新任务都会使旧任务响应失效。

### 4.2 屏幕历史与模型上下文分离

宿主现有聊天消息是屏幕事实源，内容和顺序保持原样；模块只允许追加带 marker 的可见压缩通知，不删除、重写或隐藏已经提交的宿主消息。模块另行维护：

- `summaryBaseline`：模型生成且通过全部校验的摘要 Markdown。
- `boundaryFingerprint`：摘要覆盖的历史边界及其稳定消息指纹。
- `postBoundaryMessages`：边界之后仍需发送的消息。
- `pendingRecoveryMessages`：压缩期间暂不上屏但需要恢复的 assistant/thinking/tool 消息。
- `compressionNotices`：复用现有带模块 marker 的宿主状态消息，写入宿主会话以在对应位置持久显示；请求构造时必须由 `sanitizeRequestMessages(...)` 过滤，永不发送给 Provider。

普通请求构造时，模块在请求层将模型可见消息重建为：

```text
宿主原始系统配置
+ summaryBaseline（单条合成 user 消息，使用固定包装文本）
+ boundaryFingerprint 之后的有效消息
+ 当前待发送消息（若有）
```

摘要基线沿用现有本地压缩的 `user` 角色，避免把历史中的用户或工具内容提升到 system 权限，也保持各 Provider 的角色兼容性。当前待发送消息保持自己的原始角色；不为避免连续同角色消息而拼接或改写正文。

阈值始终统计“下一次实际发给模型的有效上下文”，而不是宿主屏幕上的完整历史：尚无摘要时统计清理模块状态消息后的当前请求；已有有效摘要时统计 system 配置、摘要基线、边界后消息和必要工具定义。`pendingInput`、压缩通知和摘要请求自身用量均排除。再次压缩时只总结当前有效模型上下文，即“已有摘要 + 边界后消息”，不得重新发送已经被旧摘要覆盖、仅保留在屏幕上的原始历史。

宿主屏幕继续显示完整原始历史和模块提示。压缩过程不调用会话重载，不通过清空再恢复的方式更新界面。

## 5. 数据流

### 5.1 自动压缩

1. 宿主状态更新或完整事件回调到达模块。
2. 模块统计已完成消息的估算 token；输入框内容不参与。
3. 若未超过阈值，保持 `IDLE`。
4. 若超过阈值且 tool call/result 未闭合，进入 `WAITING_SAFE_BOUNDARY`，允许链路完成并暂缓非用户消息上屏。
5. 到达安全边界后创建任务 ID，显示“正在压缩上下文”，禁用发送/停止按钮。
6. 从当前请求快照复制配置和已完成上下文，排除触发阻塞的用户消息，追加固定摘要指令，提交隐藏摘要请求。
7. 接收模型结果后进入 `VALIDATING`：解析 Markdown、校验七段顺序和内容、校验最近轮次、校验工具配对，并组装后续请求估算 token。
8. 校验通过后以原子方式提交摘要基线，显示完成指标，恢复按钮状态。
9. 如果有被阻塞的待继续消息，先将待恢复区中的非用户事件按原顺序补充上屏，再使用新基线自动发起一次恢复请求；事件上屏与恢复请求结果解耦，且每条事件只能提交一次。
10. 如果没有待继续消息，只保留摘要基线并等待下一条用户消息。

### 5.2 用户消息触发的阻塞

用户点击发送后，用户消息先交给宿主显示层，使其立即出现在屏幕上；模块拦截实际模型请求，并以独立的 `pendingUserRequest` 保存该请求，不能依赖输入框重新构造。摘要源只包含这条消息之前已经完成的上下文。摘要成功后，模块使用“摘要 + 该用户消息”构造一次请求并解除阻塞。失败时，用户消息仍留在屏幕，`pendingUserRequest` 保持未发送，输入框中压缩期间新编辑的文本保持原样。

用户取消压缩后不自动发送 `pendingUserRequest`。下一次点击发送时先重新尝试这条已上屏请求，不重复插入用户气泡；输入框中的新文本不得越过它，须在该请求成功发起后再由用户发送。

### 5.3 手动压缩

手动压缩复用同一状态机和摘要协议，仅跳过自动阈值触发判断。手动任务仍需等待安全边界，并沿用请求快照、格式校验、后续 token 硬约束、持久化、失败、重试和本地系统提示策略。

## 6. 摘要请求与缓存

摘要请求必须在宿主请求构造层执行，复用宿主现有 Provider 链，而不是由模块重新实现各 Provider 的鉴权或协议。请求快照应保持以下内容不变：

- 当前 Provider 和模型。
- system prompt 及其序列化形式。
- 工具定义、工具顺序和工具相关参数。
- Provider 请求参数、推理参数、鉴权和请求头。
- 已完成消息的序列化字段、顺序和编码方式。

模块只在请求内容末尾追加固定摘要指令，并在内部请求标记中区分摘要任务和普通请求，避免摘要响应进入宿主聊天流。模块现有缓存策略、`prompt_cache_key`、显式缓存断点和用量处理应继续在请求层工作；摘要正文、模块 marker 和压缩提示不得成为后续 Provider 请求消息。

请求前缀的目标是稳定复用宿主配置和历史前缀。压缩后的摘要会产生新的上下文基线，首次使用该基线不要求命中旧历史缓存；后续请求必须稳定使用同一摘要文本、同一配置和同一序列化顺序，直到摘要失效或再次压缩。

## 7. 固定摘要协议

### 7.1 固定 Markdown 骨架

标题常量和模型提示词必须共用以下骨架；`N` 由任务选择的保留轮数替换为 3、2 或 1：

```markdown
## 核心任务状态
<非空正文>

## 行为设定
<非空正文>

## 分阶段的对话历史概要
<非空正文>

## 关键信息与关键上下文
<非空正文>

## 最近 N 轮格式化完整上下文
### 第 1 轮
#### user
<原始内容>
#### assistant/thinking/tool call/tool result
<按原始事件顺序完整记录>

## 当前激活的 skill/函数/工具/MCP 等包信息
<非空正文；未知时明确写“当前请求上下文未提供”，不得臆造>

## 后续执行要求
继续完成当前未结束的任务；如果没有待完成任务，则输出当前对话总结。
```

轮次小节数量必须等于 `N`，并按时间从旧到新编号。没有某类事件时不创建空角色小节；存在 tool call/result 时必须记录可配对的调用 ID、名称、参数和结果。

### 7.2 指令约束

固定摘要指令必须要求模型：

- 只输出 Markdown，不输出前后解释、代码围栏或额外标题。
- 严格按七个指定部分及顺序输出。
- 忠实保留当前任务目标、用户约束、已确认决策、重要错误和待办事项。
- 将最近 3 轮或用户选择的最近 2/1 轮按完整格式保留，不截断有效 tool call/result 配对。
- 明确列出当前激活的 skill、函数、工具、MCP 和包信息；请求中不可见的信息不得臆造。
- 最后一部分要求模型继续完成当前任务；若不存在待完成任务，则输出当前对话总结。

摘要提示词中的示例结构必须和校验器使用的标题常量一致，避免大小写、顺序或标题变体造成假失败。实现使用本节固定骨架生成提示词；任务仅替换保留轮数 `N`，并追加当前阈值和原始上下文，不允许另建一套标题文本。测试固定标题、顺序和角色小节规则。

### 7.3 校验

校验器至少检查：

1. 七个标题全部存在且严格按顺序出现。
2. 每个部分有非空正文。
3. 最近轮次数量与任务要求一致。
4. tool call 和 tool result 的 ID、顺序和配对完整；摘要响应本身必须是终止性的 assistant Markdown 文本，若模型返回 tool call、仅有 thinking 或其他结构则判定失败，且不得执行该工具。
5. 摘要文本不包含模块内部 marker 或隐藏状态字段。
6. 将摘要、系统配置、边界后的消息和待发送消息组装后，估算 token 严格小于阈值。

不能可靠解析的响应按格式失败处理，不尝试用字符串替换修复模型输出。

## 8. 持久化与失效

摘要记录按会话保存，至少包含：会话 ID、摘要文本、覆盖边界、边界指纹、Provider 签名、模型标识、保留轮数、压缩前后 token、压缩率、完成标记和更新时间。

记录采用完成标记或临时文件加原子替换：只有摘要、边界、指标和指纹全部写入后才标记可用。边界指纹只使用稳定的 role、正文、tool call ID、tool result ID 和工具调用存在性，计算前必须过滤模块状态消息与宿主瞬态字段。启动、进程恢复或切换会话时只读取已完成记录，并用当前可见历史重新计算边界指纹；指纹不匹配时立即失效，不得继续使用旧摘要。

以下操作必须使摘要失效：

- 编辑或删除摘要覆盖范围内的旧消息。
- 切换会话分支或导致边界历史变化。
- Provider、模型或关键系统配置变化。
- 摘要任务被取消、超时、失败或收到过期响应。

摘要失效不删除宿主屏幕历史和已显示的系统提示；下一次符合条件的发送或手动压缩重新建立基线。

## 9. UI 与按钮状态

模块需要维护压缩状态对 UI 的投影：

- `WAITING_SAFE_BOUNDARY`：显示等待工具链完成的本地状态。当前宿主请求必须继续运行，停止按钮维持宿主原状态；发送入口由模块阻止新请求，避免再进入一条用户消息。到达安全边界并进入 `SUMMARIZING` 后，发送和停止按钮均灰化禁用。
- `SUMMARIZING`、`RETRYING`、`VALIDATING`、`AWAITING_USER_ACTION`：发送和停止按钮灰化禁用；输入框可继续编辑。
- `IDLE`：恢复宿主按钮状态。
- 需要提供重试、保留 2 轮、保留 1 轮和取消压缩的用户操作；这些操作只能作用于当前任务。

实现应优先复用宿主现有发送/停止控件的状态更新或 Compose 重组入口；如果混淆版本没有稳定控件引用，仍必须通过发送请求拦截保证行为正确，并通过模块注入的状态层提供可见禁用状态。不得通过会话重载实现按钮或消息刷新。

## 10. 错误与并发边界

- 同一会话同时最多一个压缩任务；重复触发只更新状态，不创建并行摘要请求。
- 切换会话时取消当前任务的提交资格，但不删除已完成摘要记录。
- 旧任务的网络响应即使晚到，也只能被记录为过期响应，不能更新 UI、摘要或宿主消息。
- 摘要请求超时后执行一次完整重试；重试期间仍保持原上下文和按钮禁用。
- 所有异常路径都保留原上下文；禁止失败后回退到不受控的完整历史发送。
- Provider 返回错误、空响应、非 Markdown 响应、工具配对不完整或后续 token 超阈值均不得提交摘要。
- 摘要成功和恢复请求之间发生会话切换时，恢复请求取消，摘要仍按边界指纹保存，待再次进入会话后重新判定。

## 11. 兼容性与改动边界

实现优先沿用现有以下入口和机制：

- `ManualCompressionManager`：会话状态、状态提示、UI 刷新和压缩协调。
- `LSPilotEnhancerModule`：请求构造、请求消息替换、Provider 缓存策略和发送拦截。
- `HostAbi`：消息、Provider 配置、宿主 repository 和流式回调 ABI。
- `InjectedUiController` 与 `NativeChatTopBarAction`：模块压缩面板和状态呈现。
- `ModuleSettings`：阈值、启用开关和已有压缩设置。

现有 `ContextCompression.compact(...)` 的本地摘要算法不再作为正常自动/手动摘要路径。只有在实现阶段确认模型请求无法在当前宿主 ABI 上安全执行时，才单独评估是否保留为明确的故障降级；本设计默认失败后不发送被阻塞消息，不做无提示本地替换。

实现不得重载当前会话，不得修改已发布的宿主消息编码兼容逻辑，不得把 `_lspilot_tool_calls`、`_lspilot_tool_call_id` 等模块内部字段发送给 Provider。模块状态消息过滤必须失败关闭：若无法可靠过滤 marker 消息，则阻止该请求并提示错误，不能把未经清理的消息继续发送。

## 12. 验证方案

### 12.1 可运行检查

增加最小化的非 UI 自检，覆盖：

- 状态机合法转移和重复任务隔离。
- 用户消息从摘要源排除、恢复请求只出现一次。
- assistant/thinking/tool call/result 的暂存、顺序恢复和配对保护。
- 安全边界判断。
- 七段 Markdown 标题顺序、轮次数和工具配对校验。
- 后续请求 token 超限、重试、保留 2/1 轮和取消路径。
- 摘要记录的原子写入、完成记录读取和边界指纹失效。
- 过期任务响应不能提交状态。
- 请求层配置复制和模块状态消息过滤。

检查使用现有项目的 `assert`/运行时自检风格，不引入测试框架或 UI 自动化框架。

### 12.2 构建检查

开发完成后运行：

- `bash gradlew :app:assembleRelease`
- `bash gradlew :app:lintRelease`
- 现有压缩自检、legacy DEX ABI、DexKit ABI、ABI 缓存和 AutoRetry 检查。
- 新增摘要状态机和摘要协议自检。

### 12.3 设备人工验收

不执行 UI 自动化。设备手动验收至少包括：

1. 超过阈值后开始消息显示，发送/停止按钮灰化。
2. 输入框内容保留且不被自动发送。
3. 压缩开始、成功、失败和取消系统消息显示正确。
4. 摘要正文不上屏，原始聊天内容保持不变。
5. 用户触发请求时用户消息先上屏，压缩完成后只发送一次。
6. assistant、thinking、tool call/result 在压缩期间不上屏，恢复后顺序正确。
7. 工具调用链不会在未配对时切断。
8. 应用重启后摘要继续生效；编辑旧消息或切换分支后摘要失效。
9. 保留 2 轮、保留 1 轮和取消压缩选项行为符合设计。

## 13. 完成标准

功能只有在以下条件同时满足时才算完成：

- 自动和手动压缩都走模型摘要状态机。
- 所有摘要通过固定 Markdown、消息配对和 token 硬约束校验。
- 摘要失败不会发送未压缩的被阻塞消息。
- 宿主屏幕历史保持不变，模块系统提示可见且不进入模型上下文。
- 摘要按会话可靠持久化，并能在边界变化时失效。
- 请求层复用当前 Provider 配置和缓存路由。
- 非 UI 自检、构建和 lint 通过，设备人工验收通过。
